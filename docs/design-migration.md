# Перенос интерфейса из app

Итоговые результаты: [design-verification.md](design-verification.md).

Ветка `feat/current-app-design`, исходная версия GitHub `267a236`.

В `web/src/design` перенесены исходные компоненты кабинета, регистрации, оферты, операций и маркета. CSS, UI primitives, изображения, FAQ и RU/EN/中文 взяты из визуального образца. Папка `app/` не нужна для сборки или работы готового приложения. Cloudflare, Vinext, ChatGPT auth, D1 и R2 в runtime новой версии не используются.

## Связь с backend

Backend остаётся Go/PostgreSQL. Оригинальный движок сценариев, версии, условия, нормализованные организации/точки, загрузка файлов, авторизация и админка сохранены.

`design/bridge.ts` переводит поля визуального образца в семантические bindings оригинального API. Черновик интерфейса хранится отдельно в `cabinet_drafts`, связан с той же `questionnaire_sessions` и сохраняет неполный ввод. Отправка вызывает оригинальные `/answers` и `/complete`; клиент не назначает статус заявки. После отправки данные доступны для чтения, а изменение — через исходную процедуру возврата на доработку.

Новые PostgreSQL-миграции добавляют:

- черновики интерфейса, версионированное отдельное согласие и ознакомление с офертой;
- месячные планы и защищённый реестр фактических операций;
- селлеров, товары, файлы маркета, заказы и отзывы.

Заказ блокирует строку товара и резервирует остаток в транзакции. Повтор запроса идемпотентен. Отмена возвращает остаток ровно один раз. Состояния доставки и отзывы проверяются на сервере. Фотографии регистраций закрыты, изображения товаров доступны публично только для опубликованных карточек или владельцу. События начислений принимает только Bearer `POINT_EVENTS_SECRET`; планировщик денег не начисляет.

## Отличия, необходимые для рабочего backend

Go требует полные реквизиты, подтверждённые координаты и категории фотографий. Категория выбирается на шаге фотографий, дополнительные реквизиты и расположение подтверждаются при проверке заявки. Дополнительные вопросы опубликованного сценария также появляются при проверке. Это новые элементы в стиле исходного кабинета; проверки не отключаются ради визуального совпадения.

На шаге ИНН поиск через существующий `/api/organization-lookup` запускается автоматически после ввода полного ИНН с корректной контрольной суммой (пауза 450 мс). Название и реквизиты сохраняются в черновике, окончательное подтверждение остаётся за пользователем. Устаревший запрос отменяется при смене ИНН/формы или уходе с шага; ответ не перезаписывает название, изменённое вручную во время поиска. Есть повтор поиска и ручной ввод при ошибке сервиса. Для реальных запросов задать `DADATA_API_KEY` только в серверном `.env` и перезапустить backend; ключ не попадает в браузер.

Вход использует существующие e-mail/пароль Point. Упоминания ChatGPT и неподключённой модерации заменены фактическими подписями. Отдельные согласие и ознакомление с проектом оферты сохранены. Сохранённые подтверждения не перезаписываются. Документы обновлены в части названия авторизации и технической инфраструктуры.

Исходная админка и подробная история модерации доступны на `/admin/scenarios`, `/admin/applications`, `/applications/:id`; нового визуального аналога этих экранов в образце нет. Контакты и подтверждение доступны в кабинете и на `/verification`. Реальные платежи, SMS/email-транспорт и логистика не добавлены.

## Запуск

Нужны Node 22.13+, npm, Go 1.26.5+, PostgreSQL. При новом клонировании:

```powershell
npm ci
Copy-Item .env.example .env
# Настроить существующую PostgreSQL в DATABASE_URL.
./scripts/start.ps1 -Build
```

Не перезаписывать существующий `.env`. На этой машине создана отдельная БД `point_design` в контейнере `point-design-postgres`, порт `127.0.0.1:54329`; пароль хранится только в `.env`. Запуск контейнера: `docker start point-design-postgres`. Данные сохраняются в volume `point-design-pgdata`. Файлы — `var/uploads`.

Frontend dev — `npm run dev`, порт **5175**, API и юридические документы проксируются на 8080. Для него backend запускается с `PUBLIC_ORIGIN=http://localhost:5175`. Обычная собранная версия использует `http://localhost:8080` и такой же `PUBLIC_ORIGIN`. Origin должен точно совпадать с адресом браузера. `NEXT_PUBLIC_LANDING_URL` задаёт отдельный лендинг; после изменения нужна пересборка.

## Проверки

```powershell
npm run lint
npm test
npm run build
go vet ./cmd/... ./internal/...
# Указать TEST_DATABASE_URL на тестовую PostgreSQL:
go test ./cmd/... ./internal/... -count=1
```

Go-тесты создают и удаляют только свои временные схемы. Проверяются исходные сценарии/права/модерация и новые согласие, оферта, черновики, планы, фотографии и весь цикл маркета.

Браузерные проверки используют отдельный headless Edge с тестовым профилем, DevTools на 9223 и вторую копию backend на 8081 со схемой `point_design_browser`. Основная БД и пользовательский профиль браузера не используются. Подготовка браузера описана в [browser-tests.md](browser-tests.md).

```powershell
node scripts/design-e2e.mjs
node scripts/design-visual.mjs
node scripts/design-steps-visual.mjs
```

`design-e2e` проверяет создание аккаунта, отдельное согласие, все шаги регистрации, восстановление фотографий после refresh, реквизиты, координаты, оферту, отправку в исходную модерацию и план. `design-visual` сравнивает кабинет/регистрацию/каталог на 1440 и 390 px; `design-steps-visual` использует одинаковые браузерные фикстуры для промежуточных шагов, не записывая их в БД исходного приложения. Перед снимком фиксируется одинаковая позиция прокрутки. Для сравнения нужен работающий исходный образец на 5174. Новые backend-поля и новые для образца страницы не объявляются идентичными несуществующим эталонам.

Скриншоты и отчёты сравнения сохраняются в `var/screenshots` и не входят в Git. Автоматическое сравнение проверяет видимые области, а не все возможные пользовательские данные и состояния. Нулевое расхождение на проверенных снимках не заменяет проверку рабочего сценария.
