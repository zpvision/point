# Point

Платформа регистрации партнёров и их точек. Backend — Go 1.26 / PostgreSQL; frontend — React 19 / TypeScript / Vite. Исходный репозиторий содержал только `go.mod`, существующих компонентов или таблиц для переиспользования не было.

## Запуск

Нужны Go 1.26+, Node 22+ и PostgreSQL. Для локального запуска скопируйте `.env.example` в игнорируемый git файл `.env`, заполните настройки и выполните `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start.ps1`. Пример ручного запуска для PowerShell:

```powershell
npm.cmd ci
npm.cmd run build
$env:DATABASE_URL = 'postgresql://postgres:change-me@localhost:5432/point_dev?sslmode=disable'
$env:APP_ENV = 'development'
$env:PUBLIC_ORIGIN = 'http://localhost:8080'
go run ./cmd/point
```

Если Go не находится в PATH, локальная установка: `C:\Users\zpvis\sdk\go1.26.5\bin\go.exe`.

Открыть **http://localhost:8080**. Регистрация: `/register`; новый Point: `/points/new`; личный кабинет: `/points`; админка: `/admin/scenarios` и `/admin/applications`.

Переменные перечислены в [.env.example](.env.example). `scripts/start.ps1` загружает `.env`; при прямом `go run` передайте настройки через окружение процесса или менеджер сервиса. `APP_ENV` по умолчанию `production`: auth cookies требуют HTTPS. Для локального HTTP нужно явно `development`. `PUBLIC_ORIGIN` должен совпадать с адресом браузера, включая порт (localhost и 127.0.0.1 — разные origin).

При запуске применяются миграции и идемпотентный seed `USER_REGISTRATION` и `POINT_REGISTRATION`. Существующие сценарии seed не перезаписывает. Повторный запуск безопасен; миграции защищены advisory lock. База должна быть создана заранее.

### Первый администратор

На первый запуск передайте:

```powershell
$env:ADMIN_EMAIL = 'your-admin@example.com'
$env:ADMIN_PASSWORD = '<случайный пароль от 12 до 72 байт>'
go run ./cmd/point
```

После создания аккаунта удалите эти переменные из конфигурации. Встроенного пароля администратора нет. Bootstrap создаёт новый аккаунт, но не повышает права существующего пользователя с таким e-mail и не меняет его пароль. У bootstrap-аккаунта изначально нет телефона: если выбрать «Я» контактным лицом Point, на итоговом шаге появится ввод номера. Он сохранится в профиле перед отправкой заявки.

### Разработка frontend

Запустите backend отдельно, затем `npm.cmd run dev`. Vite проксирует `/api` на порт 8080. В backend задайте `PUBLIC_ORIGIN=http://localhost:5173` и откройте именно этот адрес. Production-сборку backend раздаёт из `web/dist`; путь можно изменить переменной `STATIC_DIR`.

## Что реализовано

- Регистрация и вход, bcrypt, защищённые HttpOnly cookies, роли partner/admin, нормализация телефона, уникальный e-mail, отдельный адаптер подтверждения контактов.
- Сценарии с разделами, 20 типами вопросов, системными bindings и custom answers. Админка: создание сценария и черновика, добавление/редактирование/дублирование/удаление вопросов, отключение, drag & drop вопросов и разделов, варианты ответа, условия, валидация, preview, публикация и read-only история версий.
- Серверный движок условий, независимые AND-группы с OR между группами; запрет циклов и ссылок вперёд. Сессия закреплена за версией. Ответы сохраняются по одному; повторная отправка обновляет ответ. При изменении ветки скрытые ответы становятся inactive и не используются для доменных данных.
- Чат с историей, редактированием ответов, прогрессом, восстановлением сессии, review, правым preview Point и адаптивной светлой монохромной темой.
- Организации и несколько Point на пользователя. Повторное использование организации по ИНН в пределах владельца. Нормализованные данные Point, расписание, фотографии, отдельные координаты адреса и входа.
- Заявки, фильтры/поиск, модерация, история комментариев, исправления и повторная отправка. Одобрение переводит Point из PENDING в ACTIVE.
- Загрузка JPEG/PNG и PDF для FILE_UPLOAD: лимит 15 МБ; до 20 попыток загрузки в минуту на владельца и до 30 на IP, проверка расширения и содержимого, проверка декодирования изображения, случайные имена, закрытое файловое хранилище, контроль доступа, прогресс/retry/delete. Файлы, загруженные до нажатия «Продолжить», также восстанавливаются после refresh.

Склады, перевозчики, маршруты и финансовые расчёты в проект не добавлены.

## Архитектура и база

См. [docs/questionnaires.md](docs/questionnaires.md).

Миграции: `internal/app/migrations/001_platform.up.sql` и `.down.sql`. Таблицы: `users`, `auth_sessions`, `organizations`, `points`, `point_applications`, `questionnaire_scenarios`, `questionnaire_versions`, `questionnaire_sessions`, `questionnaire_answers`, `attachments`, `audit_events`, `verification_challenges`, `schema_migrations`.

Граф разделов/вопросов/вариантов/условий хранится как типизированный JSONB-документ версии. Это намеренное отличие от отдельной таблицы на каждый элемент: весь граф читается одним запросом, валидируется и публикуется атомарно. Ответы и доменные сущности хранятся отдельно; Point не является одним JSON-документом. Primary key `(session_id, question_key)` исключает дубли ответов. Индексы добавлены для владельцев, версий, сессий, статуса/даты заявок, уникального e-mail и ИНН организации внутри владельца.

Опубликованный граф защищён PostgreSQL trigger от редактирования и удаления. Для изменений создаётся новый draft. При публикации текущая версия архивируется, но остаётся доступна старым сессиям. Draft использует optimistic concurrency `revision`, чтобы два администратора не перезаписали изменения друг друга.

Данные организации/Point создаются транзакционно при отправке заявки; до этого источником черновика служит session aggregate. Операционные поля читаются из `points` / `organizations`, custom answers — из сессии. Владелец организации может иметь несколько организаций и любое количество Point. Изменение реквизитов существующей организации обновляет её общие данные для точек этого владельца; ответы первоначальных заявок сохраняются в истории.

## Карты и внешние адаптеры

Используется Yandex Maps JS API **2.1**: [официальное подключение SDK](https://yandex.ru/dev/jsapi-v2-1/doc/ru/v2-1/dg/concepts/load) и [пример перетаскиваемой метки](https://yandex.ru/dev/jsapi-v2-1/doc/ru/v2-1/examples/cases/placemark). Browser SDK изолирован в `web/src/maps.tsx`, серверный геокодер и suggest — в `YandexProvider`.

```dotenv
YANDEX_MAPS_API_KEY=<ключ JavaScript API>
YANDEX_GEOCODER_API_KEY=<ключ HTTP Геокодера>
YANDEX_SUGGEST_API_KEY=<ключ Геосаджеста>
DADATA_API_KEY=<токен поиска организаций и резервного поиска адресов>
```

Browser key возвращается в `/api/me` из окружения сервера — пересборка frontend для замены ключа не требуется. Он публичен по назначению; ограничьте разрешённые домены/Referer в кабинете Yandex. Серверные ключи не отдаются frontend. Suggest и geocode проксируются через авторизованные серверные endpoints с ограничением частоты и таймаутом. Для деплоя проверьте условия использования и тарифы своего аккаунта Yandex.

Если Yandex Geocoder или Suggest недоступны, сервер автоматически использует DaData для подсказок адресов и получения координат. Для этого задайте `DADATA_API_KEY` в `.env`. Ключ остаётся только на сервере; выбранный адрес и координаты входа сохраняются в обычном формате регистрации.

HTTP Геокодер вызывается по [актуальному адресу `/v1/`](https://yandex.ru/maps-api/docs/geocoder-api/quickstart.html), Геосаджест — по [своему `/v1/suggest`](https://yandex.ru/maps-api/docs/suggest-api/request.html). Для них нужны действующие ключи соответствующих пакетов API. После выпуска ключа активация может занять до 15 минут; ответ HTTP 403 означает, что ключ отсутствует или не принимается сервисом.

При отсутствии ключей UI объясняет ошибку и позволяет ввести действительные реквизиты/координаты вручную. Данные не симулируются. Перетаскивание маркера меняет только координаты входа; reverse geocode не перезаписывает выбранный адрес. Расхождение более 1 км показывает предупреждение и не блокирует отправку. В заявке модератору доступны оба маркера и обе пары координат.

`OrganizationLookupProvider` реализован адаптером DaData; заменить его можно без изменения questionnaire engine. Данные нормализуются в `OrganizationData`. ИНН проверяется по длине и контрольной сумме.

`VerificationProvider` по умолчанию выключен и возвращает контролируемую ошибку. Контакты не объявляются подтверждёнными при регистрации. `VERIFICATION_PROVIDER=development` разрешён только при `APP_ENV=development`: одноразовый код возвращается текущему пользователю, действует 10 минут, максимум 5 попыток. В production такой запуск запрещён. Для реальных SMS/email нужно подключить транспорт провайдера к интерфейсу `Send`; страница `/account` уже использует общий API.

## Проверки

```powershell
go fmt ./cmd/... ./internal/...
go vet ./cmd/... ./internal/...
$env:TEST_DATABASE_URL = 'postgresql://postgres:change-me@localhost:5432/point_dev?sslmode=disable'
go test ./cmd/... ./internal/... -count=1
go build -o var/point.exe ./cmd/point
npm.cmd run lint
npm.cmd run typecheck
npm.cmd test
npm.cmd run build
```

Интеграционные тесты создают уникальную PostgreSQL-схему и удаляют только её в cleanup; таблицы рабочей схемы не изменяются. Без `TEST_DATABASE_URL` DB-тесты явно пропускаются. Для Go используется список собственных каталогов, чтобы не включать Go-примеры зависимостей из `node_modules`.

Browser smoke/E2E использует установленный Edge/Chrome через DevTools Protocol и встроенный Node WebSocket, без дополнительного браузерного framework. Инструкции: [docs/browser-tests.md](docs/browser-tests.md).

## Внешние зависимости перед production

- Ключи и настроенные ограничения Yandex; при необходимости токен DaData.
- Реальный транспорт SMS/email для подтверждения контактов.
- Реальные документы условий использования и обработки персональных данных: в пустом репозитории их не было. Текст CONSENT редактируется в сценарии; утверждённые ссылки нужно добавить после получения документов. Юридические тексты не выдумывались.
- Постоянный защищённый каталог `UPLOAD_DIR`, резервное копирование БД и файлов, HTTPS и корректный `PUBLIC_ORIGIN`. PDF скачиваются как attachment в sandbox; встроенные проверки не заменяют антивирусный сервис, если он требуется инфраструктурой эксплуатации.
